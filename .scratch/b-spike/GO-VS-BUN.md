# Go versus Bun + Hono comparison

Date: 2026-11-26

## Decision scope

This comparison starts from main at `23b351d`. It does not accept ADR-021 or supersede accepted ADR-020. The owner approved Debian trixie amd64 ffprobe from `ffmpeg=7:7.1.5-0+deb13u1`, package SHA-256 `8669bc77e55393c14e0dd257ba9a916007cb6da0e1074c9b5e1d53812024f2af`. This approves the package as the B-SPIKE pin. The previous Bun spike evidence used that exact package. This comparison's old Bun image contains Bun 1.4.4. The latest verified Bun release available during this run is 1.4.5, released November 19, 2026. Docker Hub denied the 1.4.5 image request with HTTP 403, so this comparison could not rerun that candidate on 1.4.5.

The comparison reuses the [isolated harness](harness/README.md) and [Bun spike raw evidence](evidence/). It reads and executes the real Go packages. It does not substitute benchmark routes or modify application source.

## Performance evidence

The only comparable request measurements currently available are the previous Bun/Node Hono DNA read workload, 800 authenticated requests at concurrency eight, on Debian 13 amd64 with 2 CPU and 1 GiB memory. Bun 1.4.4 measured p50 11.146 ms, p95 29.589 ms, zero errors and 0.945 s startup. Node 24.19.0 measured p50 18.321 ms, p95 27.185 ms, zero errors and 2.030 s startup. That is not a Go comparison and it is one run per candidate. Raw per-request samples remain in `evidence/bun-http.json` and `evidence/node-http.json`.

Go p50/p95/p99, throughput, sustained concurrency, startup, RSS, pool use, inspection throughput, and deployment image size are UNVERIFIED. The requested comparison cannot honestly rank runtime performance without running the same production API routes and PostgreSQL workload repeatedly. The Go API is not an HTTP hello-world route, and no such substitute was used.

Go has already implemented identity, workspace, DNA, Ideas, synchronous AI, V4 draft and acceptance behavior, Content views, Asset persistence/admission, S3 adapter, media inspection, API contract, and numerous package/integration tests. Existing Next.js can be retained during a staged backend/API change in either option. React/Vite is an independent frontend choice and is not required to choose Go versus Bun.

## Security findings

- The Go code has explicit SSRF screening, IP-pinned transport, TLS hostname verification, redirect revalidation, payload bounds, and policy tests. The local live TLS socket gate still needs execution.
- The previous Bun and Node transport test failed to reach the approved local address. Keep that as an unresolved critical runtime gate until the transport is corrected and retested.
- The Go worker currently executes no jobs. Persisted asset processing work will accumulate until the worker claim, fencing, retry and handler lifecycle is implemented.
- Existing npm audit recorded 25 affected package entries, including a transitive critical `proxy-addr` finding in the CLI graph. The isolated Hono harness dependencies audited at zero advisories. Recheck both against the exact lockfile and dependency scope before release.
- No live AI provider, production storage, real user account or real data was used by the Go test command.

## Recommendation

**Keep the existing Go backend and complete the worker before making a runtime migration decision.** Go currently has substantially more of the required product backend implemented and tested, including V4 drafts, acceptance, Teleprompter and Edit Guide. Bun + Hono would require extracting and wiring those product domains into a new API and implementing the worker while resolving the same SSRF, media, and operations gates.

Retain Next.js during backend completion if it shortens launch. Decide React/Vite separately after measuring its integration and maintenance cost. Revisit the runtime choice after Go's real PostgreSQL suite, local TLS pinning, actual fixture media inspection, MinIO contract, and a repeated same-route benchmark are executable in an isolated environment.
